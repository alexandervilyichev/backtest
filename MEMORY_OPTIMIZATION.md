# Оптимизация использования памяти в backtester

## Проблема

При запуске множества стратегий на больших файлах со свечами программа завершалась с ошибкой нехватки памяти (OOM - Out Of Memory).

### Причина

В методе `RunAllStrategies` в файле `internal/app/backtester/runner.go` все стратегии запускались параллельно без ограничения количества горутин:

```go
for _, name := range strategyNames {
    wg.Add(1)
    go func(strategyName string) {
        // Каждая горутина обрабатывает полный массив свечей
    }(name)
}
```

При наличии, например, 50 стратегий и файла с 100,000 свечей, все 50 горутин одновременно:
- Копируют массив свечей
- Выполняют оптимизацию параметров (grid search)
- Генерируют сигналы
- Выполняют бэктестинг

Это приводит к экспоненциальному росту потребления памяти.

## Решение

Реализован **пул воркеров (worker pool)** с ограничением количества одновременно работающих горутин:

```go
maxWorkers := runtime.NumCPU()  // Ограничиваем количеством ядер CPU

// Создаем канал задач
jobsChan := make(chan string, totalStrategies)

// Запускаем фиксированное количество воркеров
for w := 0; w < maxWorkers; w++ {
    wg.Add(1)
    go func(workerID int) {
        defer wg.Done()
        for strategyName := range jobsChan {
            // Обработка стратегии
        }
    }(w)
}

// Отправляем задачи в канал
for _, name := range strategyNames {
    jobsChan <- name
}
```

## Преимущества

1. **Контролируемое потребление памяти**: Одновременно работает только `runtime.NumCPU()` горутин вместо всех стратегий
2. **Эффективное использование CPU**: Количество воркеров соответствует количеству ядер процессора
3. **Предсказуемое поведение**: Нет риска создания тысяч горутин при добавлении новых стратегий
4. **Масштабируемость**: Работает с любым количеством стратегий и размером данных

## Результаты

- **До**: При 50 стратегиях и 100k свечей → OOM (Out Of Memory)
- **После**: При тех же условиях → стабильная работа с контролируемым потреблением памяти

## Дополнительные рекомендации

Если проблемы с памятью сохраняются, можно:

1. **Уменьшить количество воркеров через флаг**:
   ```bash
   # Использовать только 4 воркера вместо всех CPU ядер
   go run cmd/backtester/main.go --file=large_file.json --workers=4
   
   # Использовать 1 воркер (последовательное выполнение)
   go run cmd/backtester/main.go --file=large_file.json --workers=1
   ```

2. **Автоматический режим (по умолчанию)**:
   ```bash
   # Использует runtime.NumCPU() воркеров
   go run cmd/backtester/main.go --file=large_file.json --workers=0
   # или просто
   go run cmd/backtester/main.go --file=large_file.json
   ```

3. **Оптимизировать копирование данных**: Передавать указатели на массив свечей вместо копирования

4. **Использовать профилирование для анализа памяти**:
   ```bash
   # Создать профиль памяти
   go run cmd/backtester/main.go --file=large_file.json --mem_profile=mem.prof
   
   # Анализировать профиль
   go tool pprof -http=:8080 mem.prof
   
   # Или в консоли
   go tool pprof mem.prof
   > top10
   > list <function_name>
   ```

5. **Мониторинг в реальном времени**:
   ```bash
   # Запустить с HTTP профилированием
   go run cmd/backtester/main.go --file=large_file.json --prof_port=6060
   
   # В другом терминале смотреть heap
   go tool pprof http://localhost:6060/debug/pprof/heap
   ```

## Примеры использования

### Для очень больших файлов (100k+ свечей)
```bash
# Используем минимум воркеров для экономии памяти
go run cmd/backtester/main.go --file=huge_file.json --workers=2
```

### Для средних файлов (10k-50k свечей)
```bash
# Используем половину CPU для баланса скорости и памяти
go run cmd/backtester/main.go --file=medium_file.json --workers=6
```

### Для маленьких файлов (<10k свечей)
```bash
# Используем все CPU для максимальной скорости
go run cmd/backtester/main.go --file=small_file.json
```
